# Product

<!-- impeccable:product-schema 1 -->

## Platform

web

## Users

Primary users are on-shift nurses and ward staff who watch live alerts from patient-paired monitoring devices under time pressure, and need to act on them fast and without ambiguity. Secondary users are administrative roles — `super_admin`, `admin`, `ward_admin`, and capability-scoped assistant accounts — who configure wards, devices, patients, device-to-patient pairing, users, and alert settings, and who review the audit log. Access throughout is gated by fine-grained capabilities (e.g. `alerts:settings:write`, `devices:write`, `patients:write`, `pairing:write`, `wards:manage`, `users:manage:ward` / `users:manage:all`, `audit:read:ward` / `audit:read:all`, `settings:global`), not just role name.

## Product Purpose

NurseAid is a hospital nurse-call / patient-monitoring system: it pairs physical devices to patients on a ward, ingests their live signal, and raises alerts (online/offline, threshold, alert-level) to nursing staff in real time, with audit history and per-ward configuration. Success means an alert reaches the right staff, unambiguously, fast enough to act on — not visual polish for its own sake.

## Positioning

Differentiated from a traditional call-button/intercom nurse-call system by real-time IoT device-to-patient pairing plus MQTT/InfluxDB-backed live alerting and history, rather than a simple manual call/acknowledge loop.

## Operating Context

Runs in a real hospital ward, in production, with real patients and staff — not a demo or an internal tool with forgiving stakes. Backed by MQTT (device telemetry), InfluxDB (time-series), and Postgres (application data); deployed via Docker Compose behind nginx. The entire web UI is server-rendered inline HTML template strings inside `server.js` (~10.7k lines, single file). Key surfaces: `/login`, the main `ui()` shell/sidebar nav, `/wards-mgmt`, `/patients-mgmt`, `/devices-mgmt`, `/matching` (pairing), `/quick-setup` (guided pairing wizard), `/alert-settings`, `/alert-history`, `/notification-settings`, `/users-mgmt`, `/user-wards-mgmt`, `/audit-log`, `/system-mgmt` (admin: version/update management), `/export`.

**Deployment footprint: one machine.** The development machine and the production node are the same host — the Docker Compose stack running here *is* the live system. There is no fleet of ward stations, so a release affects exactly one deployment. The multi-machine update path documented in `RELEASE.md` (GitHub tags, in-app "Apply Update", auto-rollback on failed health check) exists and works, but currently has no second machine consuming it. Confirmed 2026-08-27.

**No outbound internet may be assumed at runtime.** The ward network can block external hosts, so the UI must render fully with zero external requests. As of 2026-08-27 all CSS, JS, fonts and the alert sound are served from `public/assets/`; `npm run check:assets` fails the build if any CDN URL returns.

## Capabilities and Constraints

- UI language is Thai (`<html lang="th">`); all user-facing copy, including this project's own CHANGELOG, is written in Thai. This is a durable constraint, not a placeholder.
- **Terminology:** the standard word for a patient is **ผู้ป่วย**, not คนไข้ (72 vs 24 occurrences as of 2026-08-27). New copy uses ผู้ป่วย. Never machine-translate or substitute clinical terms — "สัญญาณชีพ" must not become "signals".
- Alert-state colors (active / acknowledged / resolved, online/offline, alert severity level) are safety-critical signaling, not decorative choices — they must stay unambiguous and consistent, not be freely restyled for aesthetic variety.
- The product is under active, frequent release (CHANGELOG shows near-daily version bumps); changes are expected to ship into a live system, so backward-compatible, low-regression-risk changes are valued over exploratory rewrites.
- **There is a CSS build step.** `public/assets/tailwind.css` is a committed build artifact generated by `npm run build:css`, which scans `server.js` for the utility classes actually used. Change a utility class and you must rebuild and commit the result, or the new class ships unstyled. Tailwind is pinned to exactly `3.4.17`; v4 renames and removes utilities and would break the UI silently.
- **There is no working automated test gate.** `npm test` references `test_wards_mgmt.js`, `test_monitor_ai_chat.js` and `test_mqtt_bridge`, none of which exist in the repository or its history. Only `node --check server.js` actually runs. Verification is therefore manual: `npm run check:assets`, and Playwright screenshots of the running app in both themes.

## Product Principles

1. Clarity and correctness of an alert outrank visual expression — this is Operate-mode software for time-pressured clinical work, not a marketing surface.
2. Preserve Thai-language copy and existing alert-state color semantics; do not silently translate, reword clinical/status language, or reassign alert colors during design work.
3. Ship changes that are safe to deploy into a live hospital system — favor scoped, reviewable, low-regression-risk edits over sweeping rewrites of the single production `server.js`.
4. Respect the existing capability/role gating model when touching any page — a design change must not alter who can see or do what.
5. A visual change is not verified until someone has looked at it. Static analysis proved a CSS migration "correct" while it had silently flipped the cascade and changed real padding and margins; only a rendered screenshot would have caught that. Render the running app in both themes before claiming a UI change is done.

## Accessibility & Inclusion

**WCAG 2.2 Level AA is a binding commitment** (confirmed 2026-08-27). New and changed UI must hold it, not merely aim at it:

- Text contrast ≥ 4.5:1 against its actual surface, in **both** the light and dark themes. Tokens are the usual failure point, because every consumer inherits a token's contrast.
- A visible keyboard focus indicator on every focusable control. The shared `:focus-visible` ring carries `!important` deliberately, so a utility class cannot silently cancel it.
- Every interactive control must be a real control — reachable and activatable by keyboard. A `<div onclick>` is a defect (WCAG 2.1.1), not a style choice.
- Color is never the only signal. Alert and status indicators pair color with an icon or text, both because of color vision deficiency and because a misread alert is a patient-safety event.
- Motion respects `prefers-reduced-motion`; a global catch-all means components added later inherit the contract without their own media query.
- Text is legible at ward reading distance: no UI text below 10px.

These are verifiable, so verify them rather than assuming: compute contrast ratios against the real surface, and screenshot both themes.
